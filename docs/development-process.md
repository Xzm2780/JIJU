本文规定 JIJU 从需求确认、契约设计、任务拆分、测试、实现、评审、验证到发布和缺陷闭环的标准流程。本文不定义具体业务功能，业务范围以正式 PRD 和已批准契约为准。

## 1. 目的与适用范围

### 1.1 目的

1. 保证所有参与者基于同一套需求、契约和验收标准工作。
2. 保证权限、配额、状态、幂等、隐私和审计要求在开发前被识别。
3. 保证每个变更具备可追溯的任务、测试、提交和验证证据。
4. 减少需求遗漏、契约漂移、重复实现和不可复现的线上问题。
5. 为后续维护、交接、审计和版本演进提供统一依据。

### 1.2 适用范围

- 微信小程序页面、组件、服务和工具。
- NestJS API、领域模块、数据库和缓存。
- Prisma schema、迁移、seed 和数据清理任务。
- 运营后台页面、接口、权限和审计。
- 契约文档、任务包、测试和发布说明。

### 1.3 不在本文范围

- 具体业务规则和字段定义。
- 未获批准的产品功能。
- 真实用户数据处理授权。
- 供应商采购、法务审批和运营制度本身。

## 2. 开发原则

1. **契约先行**：接口、权限、状态、错误码和副作用先确认，再实现。
2. **服务端权威**：身份、作者、角色、配额、到期、可见性和审核结论以服务端为准。
3. **测试先行**：缺陷和功能变更先形成可失败测试，再进入实现。
4. **小批次交付**：按任务包和依赖顺序推进，避免跨多个领域的大提交。
5. **单一事实源**：文档、代码、测试和提交说明使用一致术语与定义。
6. **不可越权变更**：不得新增契约外接口、字段、依赖或客户端授权逻辑。
7. **隐私内建**：正文、评论、举报说明和身份凭据不得进入普通日志或埋点。
8. **可回滚**：数据库、配置、代码和发布变更均应具备回滚或恢复路径。

| `tests/` | 自动化、契约、性能、结构和文档校验 |

### 4.2 冲突处理

1. 安全和隐私约束高于实现便利性。
2. 技术栈和目录冲突以 `ai-context.md` 为准。
3. 实体和字段冲突以 `domain.md` 为准。
4. 对外接口行为以 `docs/api.yaml` 为准。
5. 产品范围和业务行为以正式 PRD 为准。
6. 验收覆盖以 AC 矩阵和任务包映射为准。
7. 文档无法消除冲突时，停止实现并提交明确问题，不得自行选择默认答案。

### 4.3 文档同步

接口、权限、状态、错误码、数据模型或 AC 发生变更时，同一变更批次必须检查：

- PRD 是否需要新版本。
- OpenAPI、权限矩阵、状态机和错误码是否同步。
- 领域模型和数据迁移是否同步。
- AC 矩阵和任务包依赖是否同步。
- README、测试说明和运行配置是否同步。

## 6. 需求分析与启动条件

### 6.1 需求分析步骤

1. 明确用户问题和预期结果。
2. 确认范围、非目标和明确不提供的功能。
3. 为每条可测试规则分配稳定需求 ID。
4. 补充正常路径、边界、失败和权限场景。
5. 识别 BLOCK、待确认项和外部依赖。
6. 检查是否影响权限、状态机、数据保留或审计。
7. 形成可验证 AC，不以“体验良好”等主观表述代替结果。

### 6.2 Definition of Ready

任务进入实现前必须满足：

- 需求 ID、目标和用户路径清晰。
- 功能范围和非目标明确。
- 输入、输出、错误和边界可测试。
- 权限、状态、配额、幂等和审计影响已分析。
- 涉及接口和字段的契约已批准。
- 涉及数据变更的迁移和兼容策略已评审。
- AC 已分配到测试类型和任务包。
- BLOCK 项已明确责任人和关闭标准。
- UI 文案、空态、错误态和窄屏要求已确认。

## 7. 架构与契约设计

### 7.1 设计顺序

1. 用户流程和业务边界。
2. 领域实体与字段。
3. 公开状态、审核状态和非法迁移。
4. 角色、权限和服务端校验点。
5. 接口、参数、响应和错误码。
6. 幂等、事务、配额和计数副作用。
7. 数据表、约束、索引和迁移。
8. 前端页面、组件和状态。
9. 运营后台操作与审计。

### 7.2 契约评审要求

- 每个接口明确鉴权方式、角色和数据范围。
- 请求字段明确必填、类型、格式、边界和默认值。
- 响应字段不得包含未批准字段。
- 错误码必须引用统一错误表。
- 写接口明确幂等要求、唯一约束和重试语义。
- 明确计数、配额、状态、审核和审计副作用。
- 明确是否可返回浏览量等作者专属字段。
- 明确不存在、到期、隐藏和删除状态是否统一处理。

### 7.3 设计冻结

- 技术栈、目录、ORM、数据库和缓存方案不得在任务实现中临时更换。
- 契约外接口和字段不得通过“方便调试”或“接口复用”理由加入。
- 设计需要扩大范围时，回到需求评审，不在代码评审中临时决定。

## 8. 任务拆分与执行

### 8.1 拆分规则

1. 每个任务对应一个页面或 1 至 3 个接口。
2. 每个任务不超过 5 条核心业务规则。
3. 任务必须标明前置任务、非目标和相关 AC。
4. 共享工具和能力先于业务任务实现。
5. 只读能力优先于写操作。
6. 核心业务闭环优先于运营增强和非功能优化。

### 8.2 推荐依赖顺序

1. 工程地基、公共约定和数据库基线。
2. 广场、详情和标签等只读能力。
3. 登录、会话和使用须知。
4. 发布、编辑和删除。
5. 评论和轻互动。
6. 我的帖子和个人资料。
7. 举报、治理后台和审计。
8. 性能、可观测性、隐私和数据清理。

### 8.3 任务状态

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| 待开始 | 任务包和依赖已确认 | 开始实现 |
| 进行中 | Definition of Ready 已满足 | 提交待评审 |
| 阻塞 | 存在未关闭 BLOCK 或外部依赖 | 阻塞条件解除 |
| 待验收 | 定向测试和自测完成 | 完整验证通过 |
| 完成 | 测试、审查和文档全部通过 | 已提交并记录 |

## 9. 测试先行与验收设计

### 9.1 测试循环

1. 根据 AC 编写失败测试。
2. 确认测试因预期原因失败。
3. 实现最小范围代码使测试通过。
4. 补齐边界、异常、安全和并发场景。
5. 重构并保持全部既有测试通过。

### 9.2 测试类型

| 类型 | 目标 |
| --- | --- |
| 单元测试 | 业务规则、工具函数、状态迁移和错误映射 |
| 接口测试 | 请求、响应、错误码、副作用和契约 |
| 并发测试 | 幂等、唯一约束、计数和配额 |
| 越权测试 | 游客、非作者、作者和后台角色边界 |
| UI 测试 | 页面流程、文案、空态、错误态和窄屏 |
| 性能测试 | 列表、详情和写操作 P95 与容量 |
| 文档契约测试 | PRD、OpenAPI、权限、状态、AC 和任务一致 |

### 9.3 验证结论分类

- 真实 PostgreSQL/Redis 集成运行通过。
- 生产 API 契约测试运行通过。
- 仅 mock 或静态检查通过。
- 因环境、凭据或数据条件缺失而未验证。

不得把 mock、schema 校验或文档扫描描述为真实数据库集成通过。

## 10. 前端开发流程

1. 页面只通过 `frontend/miniprogram/services/` 调用接口。
2. 客户端隐藏按钮只改善交互，不作为权限判断依据。
3. 页面状态覆盖加载、空、成功、失败、无权限和内容不可用。
4. 登录中断后保留草稿、输入和原操作意图。
5. 所有写操作生成稳定的用户意图幂等键。
6. 正文和评论按 Unicode 扩展字素簇计数，不按 UTF-16 长度截断。
7. 长文本按容器安全换行，摘要使用明确行数省略，不硬裁切字形。
8. 并排按钮和选项使用弹性布局，检查窄屏、长文案和字体放大。
9. 颜色、间距、卡片和状态样式遵循视觉设计规范。
10. 页面交付前必须通过 TypeScript 检查、前端测试和人工流程验收。

## 11. 后端开发流程

1. Controller 处理路由、协议和 DTO，不承载业务规则。
2. Service 负责权限、状态、配额、事务、幂等和副作用。
3. DTO 负责白名单字段和格式校验。
4. 数据访问通过 Prisma/Redis 基础服务完成。
5. 写操作明确事务边界，业务写入、配额和审计必须一致提交。
6. 写操作统一使用 `Idempotency-Key`，并结合数据库唯一约束和幂等记录防止重复提交，不仅依赖内存或前端。
7. 权限、到期和内容可见性不得依赖客户端字段。
8. 外部服务通过 provider 或 adapter 隔离，便于测试和替换。
9. 异常按统一错误码映射，不向客户端返回堆栈或数据库错误。
10. 日志使用字段白名单，不记录正文、评论、举报说明、凭据或身份标识。

## 12. 数据库与迁移流程

### 12.1 Schema 变更

1. 先更新 `domain.md` 和契约。
2. 再修改 Prisma schema。
3. 同步评估唯一约束、索引、查询计划和并发风险。
4. 生成迁移并审查 SQL。
5. 为模型变更补充迁移、约束和业务测试。
6. 更新 seed、测试夹具和运行说明。

### 12.2 迁移规则

- 已进入共享环境的迁移不得直接改写。
- 未交付且未离开本地环境的迁移可以在合并前重构。
- 已应用环境需要新增向前迁移。
- 字段删除前必须确认数据迁移、备份和回滚策略。
- 涉及不可逆数据删除的迁移必须单独评审。
- 开发、测试和预发布环境必须先验证迁移再进入发布。

### 12.3 验证项

- `prisma validate` 通过。
- 迁移可在空数据库按顺序执行。
- 迁移可在已有测试数据库执行。
- 新唯一约束与索引已核对。
- 数据回填、旧数据兼容和回滚路径已验证或明确标记未验证。

## 13. 运营后台开发流程

1. 后台使用独立身份、会话和角色授权。
2. 列表使用可读业务字段，不把内部对象 ID 作为主要展示内容。
3. 筛选条件使用枚举下拉或明确控件，不要求运营人员输入内部代码。
4. 列表按业务状态显示可执行操作；终态记录显示终态文字，不显示“处理”。
5. 内容处理、账号处置和复核在独立工作标签或处理页完成。
6. 所有治理写入必须记录操作人、角色、对象、版本、原因和前后状态。
7. 已完成、已删除、已到期、已判定违规等状态不得再次提供无效操作。
8. 成功、失败、状态冲突和不可用必须使用明确反馈。
9. 后台不得展示开发说明、内部枚举或实现细节。

## 14. 代码评审流程

### 14.1 提交评审前

- 变更范围与任务包一致。
- 没有覆盖无关未提交修改。
- 新增或修改了对应测试。
- 定向测试、完整测试和构建通过。
- 文档、契约和迁移已同步。
- 提交说明能说明用户可见结果。

### 14.2 评审检查

| 维度 | 检查内容 |
| --- | --- |
| 契约 | 路径、字段、错误码、状态和响应无漂移 |
| 权限 | 未登录、非作者、作者和运营角色均覆盖 |
| 数据 | 事务、唯一约束、索引、计数和迁移安全 |
| 并发 | 幂等、重复点击、重复请求和竞争条件 |
| 安全隐私 | 无正文入日志、无凭据泄露、无客户端授权 |
| 可维护性 | 职责清晰、命名一致、无无关重构 |
| 测试 | 正常、边界、异常、越权和回归可验证 |
| 后台体验 | 终态不可操作、文案可读、无内部说明 |

### 14.3 评审结论

- **通过**：可以进入完整验证。
- **有条件通过**：仅允许处理明确的非阻断项，并保留跟踪。
- **退回修改**：存在契约、权限、数据、安全或测试缺口。

## 15. 测试与质量门禁

| 门禁 | 要求 | 证据 |
| --- | --- | --- |

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/production/Verify-Production.ps1
```

任何失败、跳过或未验证项必须记录原因，不得用“其他测试通过”掩盖。

## 16. 缺陷处理流程

```mermaid
flowchart LR
    A["发现缺陷"] --> B["记录请求ID与环境"]
    B --> C["复现并定位"]
    C --> D["补失败测试"]
    D --> E["修复"]
    E --> F["定向验证"]
    F --> G["完整回归"]
    G --> H["关闭并记录根因"]
```

### 16.1 缺陷记录

- 用户可见现象。
- 发生时间、环境和版本。
- `request_id`、接口和操作步骤。
- 预期结果与实际结果。
- 影响范围、是否可重复和是否有数据副作用。
- 涉及任务包、AC 和前置数据。

### 16.2 修复规则

1. 先复现并确认根因。
2. 写一个在修复前失败的回归测试。
3. 修复范围最小化，不夹带无关重构。
4. 验证原问题、相邻场景和回归测试。
5. 涉及数据修复时，迁移或修复脚本必须单独评审。
6. 完成后记录根因、修复范围和预防措施。

## 17. 阻塞项与决策管理

### 17.1 BLOCK 管理

每条 BLOCK 必须包含：

- 唯一编号和事项描述。
- 影响的需求、接口或任务。
- 当前状态和责任人。
- 关闭标准和所需证据。
- 阻塞期间允许和禁止的工作。

BLOCK 未关闭时：

- 不得通过代码默认值代替业务决策。
- 不得对外宣称相关能力已完成。
- 可以通过 mock、配置或接口边界推进不依赖该决策的工作。
- 测试结果必须标记未验证范围。

### 17.2 决策记录

重要决策至少记录：

- 决策时间和参与人。
- 背景与约束。
- 备选方案。
- 最终选择和理由。
- 影响的文档、接口、数据和测试。
- 后续复查条件。

## 18. 版本、提交与发布

### 18.1 版本规则

- PRD 文件名与文档 ID、内部版本保持一致。
- 正式 PRD 使用稳定版本号，历史版本只用于追溯。
- 破坏性契约变化必须显式升级版本。
- 数据迁移和接口变更在同一发布计划中说明先后顺序。

### 18.2 提交规则

1. 每个可交付变更对应一个可追踪提交。
2. 提交前排除无关未提交修改。
3. 提交说明描述结果，不使用“修改代码”“更新文件”等空泛表述。
4. 代码、测试和必要文档尽量在同一提交中保持一致。
5. 不提交 `.env`、凭据、日志、真实用户数据或本地开发配置。

### 18.3 发布前检查

- PRD、契约、迁移和文档版本一致。
- 所有必测项目和回归测试通过。
- 数据库备份、迁移顺序和回滚路径明确。
- 环境变量、域名、缓存和外部服务可用。
- 后台角色和运营账号具备正确权限。
- 监控、错误请求和回滚责任人已确认。
- 未验证项已明确记录，未作为已验证能力宣称。

### 18.4 发布后检查

- 核心读路径和写路径可用。
- 数据库迁移版本正确。
- 登录、发布、评论、互动和后台流程抽查通过。
- 错误率和延迟无异常。
- 审计日志正常生成。
- 回滚触发条件明确。

## 19. 完成定义与质量指标

### 19.1 单个任务 Definition of Done

- 范围内功能全部实现。
- 非目标未被意外加入。
- 核心规则不超过任务包约定范围。
- 单元、接口、并发、越权或 UI 测试按要求补充。
- 相关 AC 有明确证据。
- 后端测试、构建和前端检查通过。
- 契约、数据和运行文档已同步。
- 代码评审通过。
- 已创建可追踪提交。
- 无已知阻断缺陷或未记录风险。

### 19.2 单个接口 Definition of Done

- 路径、请求和响应符合 OpenAPI。
- 鉴权和角色由服务端执行。
- 错误码和用户文案符合统一错误表。
- 幂等和重复请求行为明确。
- 事务和唯一约束保障并发安全。
- 副作用、配额、计数和审计已验证。
- 不泄露不存在性、浏览量或作者专属信息。

### 19.3 单个页面 Definition of Done

- 覆盖加载、空、成功、错误和内容不可用状态。
- 登录中断和返回路径正常。
- 长文本、窄屏、字体放大和按钮组无重叠。
- 客户端不展示内部 ID、技术错误或开发提示。
- 权限操作由服务端结果驱动。
- 自动化测试和人工验收均完成。
